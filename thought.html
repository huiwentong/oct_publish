Core Summary

为什么要重新设计？

原有 publish 工具框架日渐老旧，无法满足 AI 时代的需求

🧩

框架老化

原有 publish 工具框架十分老旧，设计思路已不再符合日益变化的技术需求，亟需现代化重构。

🤖

AI 接入壁垒

纯 UI 操作式工具无法被 AI 工作流调用，AI agent 对现有界面无从下手，阻碍智能化升级。

📦

批量发布困境

外包回收或批量发布时需手动编写重复脚本模拟操作，流程更新时所有脚本需同步修改，维护繁琐。

📋

Log 方式滞后

日志方式和发布设计与现代技术框架脱节，发布版本时的体验感不够顺畅。

按环节分配组件开发任务，优先升级小简单环节，试行稳定后逐步推广，新旧工具可同时运行。

Design Requirements

设计需求

新 publish 工具需要满足的核心能力与设计原则

1

🖥️ UI + CLI 双模式

支持 UI 操作与 CLI 操作，两种方式调用相同核心逻辑。CLI 模式满足批量快速发布、外包回收等自动化场景。

2

🗄️ 数据库日志存储

使用数据库存放日志，支持快速定位、查找与回溯汇总，日志也可通过命令在 UI 中展示。

3

📝 良好注释 · AI 友好

尽可能做好代码与配置注释，便于 AI agent 辅助发布操作、自动抓取问题并快速分析。

4

🧱 三层解耦架构

拆分为三个互不耦合的独立部分：UI 层、核心逻辑层、可自由组装的发布组件层。

5

🛠️ 后台脚本服务

UI 启动时可运行后台脚本服务，对目标机器远程执行 DCC 命令进行快速纠错，无需亲临工位。

🎨 UI 层

🖥️

QtPy 兼容框架

使用 QtPy 作为抽象层，兼容不同版本的 Qt 框架和 PyQt/PySide 绑定，界面结构清晰简单。

🔄

内嵌服务组件

UI 启动后服务同步启动直至程序退出；等待外部 Python/Cmd 指令并执行，将结果反馈给请求客户端。

⚙️ 核心逻辑层

📥

参数入口 & 缓存

提供标准参数入口；发布状态缓存支持失败重启后的断点续传，发布结束自动清理。

🐛

快速 Debug 组件

在核心启动环境中可快速调用单个组件执行，并检查执行结果与 stdout 内容。
